Product overview
[APP NAME] is a video-first local marketplace: sellers post short vertical video adverts (15–60 s) of items for sale, starting with used cars. Buyers scroll a full-screen, TikTok-style feed, message the seller in-app, and arrange a viewing in person, as they would on Facebook Marketplace.
Core user journeys:
1. Seller posts. Signs up, verifies phone number, records or uploads a video, adds structured details (make, model, year, mileage, fuel, transmission, price, location), publishes.
2. Buyer browses. Scrolls the feed filtered by distance, price and make; taps through to listing details; saves listings.
3. Buyer contacts seller. Taps Message on a listing; both chat in real time.
4. Viewing arranged. Either party proposes a time and public meeting place in the chat; the other accepts, declines or counters.
5. Sale closes. Seller marks the listing sold and it leaves the feed. Money changes hands in person; there are no in-app payments.
6. Safety. Anyone can report or block a listing or user; moderators review reports.
7. Dealer seeding. A verified dealer account can bulk-upload many listings (CSV of details plus videos) so the feed has stock at launch.
MVP scope
The MVP is cars only, in one region ([LAUNCH REGION]), on a mobile-first responsive web app. Design every module so a second category or region is configuration, not a rewrite.
In the MVP
• Phone-verified accounts (private sellers, buyers, dealers) and an admin role
• Video upload, processing and adaptive playback
• Feed with distance, price, make and year filters; listing detail page; saved listings
• 1:1 real-time messaging with push and email notifications
• Structured viewing proposals inside the chat
• Report, block, and an admin moderation queue
• Dealer bulk upload (CSV plus videos)
• Basic analytics events (impressions, watch time, saves, messages)
Later, not now
• In-app payments or escrow
• Native iOS and Android apps
• A learned recommendation model
• Categories beyond cars, and multiple regions or languages
• In-app video editing beyond trimming
• Vehicle history checks by registration

Architecture
Use a modular monolith: one FastAPI codebase split into domain modules, deployed as stateless API containers plus separate worker containers. Split a module into its own service only when load or ownership demands it, and name which module would go first.
Modules: auth, users, listings, media, feed, messaging, viewings, moderation, notifications, analytics. Modules talk through service interfaces or domain events, never by querying each other's tables.
Request paths:
• Video segments, posters and the static React build come from the CDN.
• API and WebSocket traffic goes client → Nginx → FastAPI.
• FastAPI reads and writes Postgres, uses Redis for cache, rate limits and pub/sub, and enqueues slow work.
• Workers process uploads, run moderation scans and send push and email notifications.

Core flows
Design these four flows in detail; they carry most of the load and most of the risk.
Upload and video pipeline
1. Client asks to upload; the API creates a listing in draft and returns a presigned multipart upload URL (limits: [60 s], [500 MB], MP4 or MOV).
2. Client uploads straight to object storage.
3. A completion callback enqueues a job: validate, transcode to HLS renditions, make a poster frame and thumbnails, strip location metadata, run automated moderation.
4. Listing moves processing → pending_review or live. Jobs are idempotent, retry with backoff and land in a dead-letter queue on repeated failure.
5. Client learns the status by WebSocket event, with polling as a fallback.
Feed
• Cursor-based pagination only, never offset.
• MVP ranking: listings within the buyer's radius and filters, ordered by recency with simple boosts for engagement (watch-through, saves, messages) and penalties for already-seen items.
• Put ranking behind a FeedRanker interface so a learned model can replace it later.
• Cache candidate sets per geographic cell in Redis with a short TTL; apply per-user filtering on top.
• Client plays only the visible video, preloads the next two at low bitrate, and releases off-screen players.
• Client sends impression and watch events in batches to an events endpoint; store them append-only for ranking and analytics.
Messaging
• One conversation per (listing, buyer) pair.
• Send over REST with a client-generated idempotency key; persist first, then deliver over WebSocket.
• Fan out across API instances with Redis pub/sub; offline recipients get a push notification.
• Read receipts; typing indicators are optional.
• Phone numbers and emails stay hidden unless a user chooses to share them.
• Flag messages with common scam patterns, such as deposit requests, off-platform payment links and courier stories, and warn the recipient.
• Block and report from any conversation.
Viewings
• Either party proposes a structured viewing (time plus place) inside the chat; the other accepts, declines or counters.
• Prompt users towards busy public meeting places and show safety tips before the first viewing.
• Send reminders and offer a calendar (.ics) export.

Trust, safety and compliance
Scams and fake listings kill used-car marketplaces, so treat trust and safety as a core module, not a later add-on.
• Verification: SMS OTP required to post or message; a verified badge for dealers; sellers must be 18+.
• Content rights: uploaders confirm they own the video and the item. The platform hosts no scraped or third-party content.
• Automated moderation: scan sampled video frames and listing text for prohibited content and contact details; route hits to human review.
• Fraud signals: rate limits on new accounts, duplicate-video detection by perceptual hash, price-anomaly flags, scam-pattern detection in chat, warning banners.
• Moderation tooling: an admin queue with actions (approve, remove, suspend), reasons recorded, notifications to the affected user, and an appeal path.
• Privacy (GDPR): data minimisation, consent for non-essential analytics, export and delete-my-data endpoints, retention periods for messages, videos and events, EU data residency.
• EU Digital Services Act: list which obligations apply to a small marketplace at launch (such as notice-and-action reporting and statements of reasons for removals), which arrive as it grows, and how the design meets each. Flag this section for legal review.
Code quality and repo structure
Readable beats clever: someone new should find any feature's code in under a minute.
• Monorepo: /backend, /frontend, /infra, /docs.
• Backend layering per module: router (HTTP only) → service (business logic) → repository (database) → models and schemas. No database calls in routers; dependencies injected with FastAPI Depends.
• Frontend by feature: features/feed, features/listing, features/chat, features/viewings, plus shared components, hooks and the generated API client.
• Config: pydantic-settings, environment variables, no secrets in the repo.
• Typing and linting: mypy strict and Ruff on the backend; TypeScript strict, ESLint and Prettier on the frontend.
• Tests: pytest unit tests on services; integration tests against real Postgres and Redis in containers; Vitest and React Testing Library; one Playwright end-to-end test for upload → feed → message → viewing.
• CI: lint, typecheck, test, migration check and image build on every pull request.
• Docs: README with one-command local setup (docker compose up), and a short architecture decision record for each major choice.
• Style: small functions, descriptive names, docstrings on public service methods, no abstraction until the second use case.
